# 学习闭环：实施阶段与发布边界

本文件是 [学习闭环总览](../learning-loop.md) 的**第八、九章**。章节号在总览里连续编号，跨文件引用按「§几」写。
## 八、实施阶段与验收

**各阶段共同要求（超出验收之外）**：用户能感知的行为改了（今天做什么、计划里有什么、界面与文案），
同一个提交里改 `docs/user/learning/mobile.md`，含它的「当前版本范围」一节。
每个阶段至少有一条可自动跑的测试留在仓库里，不靠人肉点一遍就算过。

**现状**：Android 的 JVM 单元测试已接进 CI（`.github/workflows/ci.yml` 的 `android` job，走 `gradlew` + `setup-java 17` + `prepare.py` 取依赖）；中继与 Rust 侧本来就在 CI 里。

### 阶段0A：修复来源，建立可验证输入

- [x] 修复词库ISO日期解析：**日期缺失或非法时整行跳过**（与桌面端 `file.rs:52-53` 的 `?` 短路一致），只记 `invalid_date_rows` 计数；确定新旧手机/电脑的日期协议并同步修改Transfer。`last` 字段仍是 UTC 午夜的 Unix 秒数（旧接口契约不变），手机端拿不到就记 0 表示未知，不再写 1970 或当前时间。
- [x] 顺带修掉连接工具的错误回复丢响应：错误回复前必须把请求体读干净。带着没读完的请求体关连接，Windows 发 RST 而不是 FIN，客户端只看到「连接被中止」，手机端于是把「配对地址无效」显示成笼统的「同步失败」。这也是仓库里测试偶发失败（约一半）的原因。
- [x] 实现上下文路由 `GET /api/learning/context`、字段/字节上限及稳定截断；**只此一个来源接口**，旧 `/api/learning/words` 不动；暂不采集应用名。窗口只按 `last` 过滤（上游没有逐日历史），截断按 `committed` 降序、`language/english` 升序稳定排序并报 `total` 与 `truncated`。
- [x] 上下文里带上**个人释义表**：桌面端读 `user-glossary-<语言>.tsv`（与 `user-vocab.tsv` 同目录，纯 TSV）整份发出，**差集在手机端做**——手机用本地随包表比对后再合并，个人表优先。桌面端不读 `.qj`。
- [x] 手机端把个人释义表并进本地表：`Transfer` 读 `glosses`，经 `GlossaryJson.toPersonalGlosses()` + `PersonalGlosses.of()` 做差集（个人表优先、随包表兜底），结果由 `learning/glossary/GlossaryStore.kt` 持久化到 `learning_glossaries`。随包表还没有下载通道时 `table` 为 null，个人释义全留——这是协议约定的降级，不是错误。
- [x] 静态表进 `data` Release 的方式定下来：`tools/release/data-bundle.sh` 现在除了 `qingjian-data.tar.gz`，还把 `glossary-en.qj` / `glossary-zh.qj` 作为**独立资产**上传，SHA-256 一并写进 `tools/release/data.lock`；手机只下这两张表，不必下整个 42MB 数据包。
- [x] 手机侧写 `.qj` 只读器（中→英的 `glossary-en` 与英→中的 `glossary-zh` 两张，同一个表无关读器，不复刻哈希）+ 用合成的迷你 `.qj` 做测试。**已做只读器**（`learning/glossary/Glossary.kt`）：精确查走二分，子串搜索扫一遍词条表，都不建内存索引；JVM 单元测试覆盖，并额外读一次本机真实产品词表（23 万条）验布局与耗时。
- [x] 静态表的**随包分发与校验**：两张表由 `prepare.py` 按 `dependencies.json` 下载校验后放进 `app/src/main/assets/glossaries/`，随 APK 打包、`noCompress` 保留 `.qj`；首次使用时 `GlossaryFiles` 释放到私有目录再 mmap，装完即可离线查词，不需要联网。实测 23.2 万条 / 4.5 万条可查（`候选 → n. candidate`、`deploy → 部署`、大小写混合的 `Deploy` 同样命中）。二进制不入 Git，与 AAR、模型同一约定。
- [x] 静态表的**更新通道**：`learning/glossary/GlossaryDownload.kt` 按 `data-vN` 的公开地址下载，先写 `.download` 临时文件，长度与 SHA-256 都校验通过才原子替换——断线不留半截、哈希不符不破坏已装好的表；`GlossaryInstall.kt` 的判定规则有 JVM 测试。设置页「数据与关于 → 检查词汇表更新」是入口。**当前哈希尚未填**（`GlossaryRelease.HASHES` 为空）：`data-v7` 只发了 `qingjian-data.tar.gz`，没有这两份独立资产；下一次 `data-bundle.sh` 发版后把 `data.lock` 里的两行抄过来即可。未填时随包表照常工作，界面说明「已是最新」。
- [x] 引入 JVM 单元测试层（`junit:junit:4.13.2`）：纯逻辑（文件解析、字段裁剪、合并优先级、协议回退）放这里，秒级反馈；UI 与跨进程流程仍用 instrumentation 探针。
- [x] 来源、上下文、备份分离错误处理，兼容404，不覆盖非空手机笔记。`Transfer.run()` 拆成拉来源 / 传备份 / 刷新状态三步，各自 `runCatching` 隔离，一步失败不阻断另两步；先试 `/api/learning/context`，**只有 404** 才退回旧的 `/api/learning/words`（401/403 提示配对失效、其它码报失败并保留上次数据）；写库只在 `words.meaning` 为空时补笔记，不覆盖非空。
- [x] 同步 `CLAUDE.md` 目录地图：补 `apps/android-speech`（Android 学习与朗读 App，Kotlin，独立于 Rust workspace，不参与主发版）与 `tools/speech-relay`（电脑↔手机配对中继，Python）；顺带补 `tools/eval`、`tools/release`。
- 验收：上游真实格式的七列/十列样例都能返回词；**日期非法的行两端都跳过**（中继端与桌面端对「这个词是否存在」的判断一致，用同一份坏日期 fixture 交叉验证）；构建30/31与新版的协议兼容；401、404、截断、失败保留、独立备份路径均有测试。
  **现状**：七列/十列、坏日期、401、截断、备份已有测试；**坏日期与桌面端的交叉 fixture、404 回退、构建30/31 兼容均未做**。
- 验收：手机能用合成的迷你 `.qj` 读出词与释义（**不拿随包大表当测试材料**）；大小写混合的英文键返回同一条；下载中断不留下半截文件，SHA-256 不符不替换已装好的表。
  **现状**：迷你 `.qj` 与真实表布局已验；**大小写混合返回同一条随只读器的 ASCII 小写回退一起补**；下载与校验未做，无从验。
- 验收：桌面端发的个人释义表是**原样整份**（与 `user-glossary-<语言>.tsv` 逐行一致）；手机端并入后**本地表里只多出随包表没有的词**（用同一份 fixture 交叉验证桌面与手机两端判断一致）；差集为空时不报错；差集里的词在手机端优先于随包表。
  **现状**：桌面端发的是解析后的结构化条目（不是逐行原样），且条数上限 2000、单条 `text` 截 500 字，超限时以 `glosses_truncated` 报出；手机端差集规则有 JVM 测试，但**未接线**。

### 阶段1：真正可离线执行的本机今日计划

- [ ] 实现Pack、PlanBuilder、统一PlanConstraints和本机理由；首页直接展示可开始的任务。
- [ ] 新计划CREATE直接走本机校验与提交，不再触发旧模型选词入口；只对旧格式计划保留原恢复流程，阶段2再增加可选模型修订。
- [ ] 新执行器落实固定stage_key、草稿、暂停/恢复、显式放弃和按环节完成率。
- [ ] 词条记 `gloss_origin`（`desktop-vocab` / `static-table` / `ai` / `unknown`）；桌面已给词义时 `prepare_word_materials` **只补 example / translation / collocations / usage**，不重造 meaning。
- [ ] 词条编辑接受中文输入：中文查静态表得到英文词，英文做主键、中文做释义落库（与桌面上屏中文候选显示英文译词同一条路径）。
- [ ] **词库页搜索框扩成两个来源**：本机已添加的词（现状）+ 静态表里未添加的词。命中静态表时显示词行 + 词性 + 中文释义，给「加入词库」；加入后英文做主键，例句 / 搭配 / 用法标「待补充」。
- [ ] `notes/Agent.kt` 的 `prepare_word_materials` 改成**只补 example / translation / collocations / usage**，meaning 与词性以静态表为准，不让模型重造。
- [ ] 缺例句、缺干扰项、无音频时按明确规则降级，不请求模型也能完成已有材料任务。
- 验收：11个到期词+多个新词时不超过10项；同一词四个到期维度不覆盖丢失或重复扣预算；预算及credit总和精确一致。
- 验收：零词、一词、仅电脑来源、全部solid、两分钟预算、旧轮未完成、同日加练均有fixture；同快照同日期同结果；320dp、键盘和断网主要流程通过。
- 验收：桌面已给词义的词，模型请求里不再重复出现 meaning 字段；`gloss_origin` 四个取值各有一个 fixture。
- 验收：词条编辑输入中文词（如「候选」）能查到英文并落库为主键；输入英文词能查到中文填进释义；两向查不到的都留空并标 `unknown`。
- 验收：词库页搜索「候选」能同时列出已添加的词与静态表里的词，静态表那一条能「加入词库」；加入后「让 AI 补充」只补四项、meaning 不被模型改写；未下载表时搜索框仍能用（只搜本机词）并给出「还没下载词汇表」的提示。

### 阶段2：有成本上限的模型修订与自适应

- [ ] 改造每日Koog执行路径，直接传Pack，提案后终止，共用最多2次HTTP请求预算。
- [ ] 加修订逐条校验、请求/取消反馈、规则拒绝理由；已完成结果不可变。
- [ ] 接入真实credit反馈、有效测时、偏好revision及派生factor、跳过避让。
- 验收：0/1/2请求的真实传输计数；无隐式读事实或收尾第三次；缺材料超过3词时明确延期。
- 验收：按 `docs/plan/model-eval.md` 的尺子留基线对比——改造前每日3次请求、采纳率与完成率均无基线值；改造后请求数≤2，并首次记下采纳率与完成率的基线值，后续改动一律与该基线比。
- 验收：三天低完成率降为0.8；未满三天、零分母、测时未知和偏好变更正确回到1.0或不触发加速；用户“只做一题”不被factor/模型放宽。

### 阶段3：可选应用聚合与跨端意图

- [ ] 基于有直接关联的译词日聚合补应用分布；不推断历史无关联记录。
- [ ] 用户明确表达“想练X”时保存待练意图，带来源、去重键和过期时间。
- [ ] 电脑“加入手机待练”需独立的电脑到手机拉取队列与确认，不能反用手机上传备份接口。
- 验收：应用采集开关、30日过期、重启去重、来源未知；意图不重复消费、离线排队、清空后不复活。仅识别文字意图不赋予任意修改偏好或成绩的权限。

## 九、发布边界与仍可后置的工作

- 本阶段修改计划，不代表以上开发完成。实际实施分段交付，每段都保留可工作的旧流程。
- 不做后台定时学习推送、通知提醒、外部云存储或账号；现有临时公网HTTPS配对继续兼容。
- 不上传新增输入原文、键串或完整输入日志；origin_text/example只沿用已授权的来源字段。应用名是独立可选数据。
- 静态译词表是随包的公开数据，**下发到手机后查询全在本地完成，不新增任何网络请求**（见 §2.2）。
- 静态译词表本阶段只做**英文这一门**的两张：中→英的 `glossary-en`（主力）与英→中的 `glossary-zh`（辅助）；ja/de/es/vi 的表不在这一版，日语等语言的词条仍走生词本同步或 AI。
- `glossary-zh` 的覆盖扩充（`gloss-gen english --min-frequency` 从 2500 降到 1000，4.5 万 → 8 万词）是**数据生成任务**，不在本计划的代码改动里；静态表查不到时记 `unknown` 走 AI 兜底。反向翻译不是解法，理由见 §2.2。
- 随包表的版本跟产品的 `data-vN` Release 走，**不走电脑同步**；桌面的表也是同一个 Release 装的。桌面比手机多知道的是**个人释义表**，随 `/api/learning/context` 按差集下发（见 §2.2）。手机 → 桌面沿用现有备份通道，不新增。
- 不做向量检索、自动职业画像，也不将AI记忆当作学习成绩。
- 后续可再细化理由语气、提示主动提问的时机、跨端意图具体字段，以及其他语言的专门适配；事件契约、幂等恢复、schema、请求计数和关键fixture不能继续列为“以后再定”。
- 真机覆盖安装、锁屏切网、真实TTS/录音和真实模型教学效果须单独验证；单元测试与模拟器结果不能代替这些结论。
