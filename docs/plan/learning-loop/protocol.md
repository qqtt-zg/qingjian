# 学习闭环：数据接入与协议

本文件是 [学习闭环总览](../learning-loop.md) 的**第二章**。章节号在总览里连续编号，跨文件引用按「§几」写。
## 二、数据接入与协议

### 2.1 第一批只接可靠的电脑来源

新增 `GET /api/learning/context`，沿用配对鉴权、原端口及HTTPS链路。阶段0不从输入日志推断英文词的应用分布。

```json
{
  "schema": 1,
  "generated_at": "2026-10-21T09:00:00+08:00",
  "days": 30,
  "apps_status": "not_collected",
  "truncated": false,
  "words": [
    {
      "language": "en",
      "english": "deploy",
      "seen": 42,
      "committed": 11,
      "used": 3,
      "first": "2026-08-01",
      "last": "2026-10-18",
      "desktop_known": false,
      "origin_text": "部署到测试环境",
      "example": "把这个版本部署到测试环境",
      "apps": null
    }
  ]
}
```

**术语约定（全文通用）**：三个「来源」不是一件事，字段名不共用——
`origin_text` = 词的中文来源（字符串，来自词汇本第 9 列）；
`origin` = 数据归属（phone/desktop/both，能力投影用）；
`event_id` 的前缀 = 事件来源命名空间（哪个物理表来的）。
`desktopRevision` = 电脑来源数据的修订号（快照里带上，改了来源才重算）。
输入日志里既有的 `CommitEntry.source` 是候选来源类型（词 / 整句 / 译词 / 云端），与本计划无关，读到时不要对齐。

- 三项词库计数沿用原有累计值。`days: 30` 是候选筛选窗口，不将累计计数伪称为“最近30天使用次数”。
- **`english` 就是译词**（桌面生词本第 2 列），不是「英文模式下打的词」。命名沿用旧接口 `/api/learning/words`，手机词条主键就是它。
- 桌面**从没遇到过的词**不在这个响应里（生词本只记遇到过的），这类词的释义走静态表，见 [2.2](#22-静态译词表下发只做英文)。
- **窗口的过滤依据必须写死**：上游 `user-vocab.tsv` 只有 `first/last` 两个日期、没有逐日历史，因此窗口只能按 `last >= 今天 − 30天` 过滤（不是 `first`，也不是“30天内出现过”的逐日口径）。副作用要写进契约：30天没碰的词不会出现在响应里，手机侧因此看不到它的累计计数。**这不是“词被删除”**，手机不得据此清空已有记录；响应里不返回该词即表示“窗口外”，不是“不存在”。
- `origin_text/example` 仅复用现有词库内容；不另外上传输入日志、键串、候选列表或应用内上下文。
- 每个字段限定类型与长度；按UTF-8字节计响应上限2MiB。截断时按 `committed` 降序、`language/english` 升序稳定排序，并返回 `truncated: true` 和总数。
- 404表示旧工具不支持，退回旧 `/api/learning/words` 路由。401显示配对失效；暂时失败保留上次来源并标注时间，不将“获取失败”解释为“所有词已删除”。
- 截断结果只合并返回条目，不删除未返回来源。来源刷新、能力重算与备份分别记录结果，某一步失败不阻断其他步骤。
- 手机按词库日期做日级排序；真实答题时间统一UTC毫秒。计划另存生成时的日期和时区，不能混用日期、秒数、毫秒。
- 旧版 `Transfer.run()` 的单个try块需要拆开，不能仅在文档中声称“任一步失败互不影响”。

### 2.2 静态译词表下发（只做英文）

**桌面端的译词本来就是静态的**，不需要 AI：

| 来源 | 是什么 | 静态吗 | 含什么 |
| --- | --- | --- | --- |
| 随包静态表 `glossary-<语言>.qj` | LLM **离线批量生成**后随包分发 | **纯静态** | `词` → `[词性. ]译词[|读音]`，每词最多 2 条释义。**没有例句、没有搭配、没有用法**——`gloss-gen` 的提示词里明写「不要例句」 |
| 个人释义表 `user-glossary-<语言>.tsv` | 云端释义兜底回流后固化 | 半静态（AI 生成一次，落盘后不再实时调） | 同上。**个人表优先、随包表兜底**（`LayeredTranslator`） |
| 生词本 `user-vocab.tsv` 第 2 列「译词」 | 前两者的**快照** | 静态 | 译词 + 计数 + 首末见 + 中文来源 + 例句 |

英文候选的中文释义**不记进生词本**（`crates/qingjian-core/src/engine/commit/mod.rs:202-204`），那是另一个方向。

**手机端已有的**：`learning/archive/Transfer.kt:38-40` 已经把桌面生词本的译词当手机词条主键同步过去、把第 9 列「中文」同步进 `words.meaning`。所以**用户在电脑上遇到过的词，手机已经有译词和中文释义，不需要 AI**。

**还缺的两件事**：

1. 手机同步后 `word_materials` 是空的，英文例句/搭配/用法仍要手机自己调 Koog 生成——**这部分本来也必须 AI**，静态表给不了。
2. 桌面端**从没遇到过的词**，手机没有中文释义。这条本节解决。

#### 两张表都服务，但定位不同

手机的词条模型是**英文词为主键 + 中文释义**（`learning/WordEditor.kt` 的输入框叫「英文单词或短语」和「中文笔记」，英文建后不可改；测验 `CHOICE` 是英文选中文）。但**词表质量比键的方向更要紧**，所以两张表都服务：

| 表 | 方向 | 词数 | 定位 | 手机侧用途 |
| --- | --- | --- | --- | --- |
| `glossary-en.qj` | 中 → 英 | 232,213 | **主力**。覆盖产品词库 + 短语层，是**按这个应用的域生成**的 | 用户输入**中文词** → 查出英文词 + 词性 → 建词。**与桌面上屏中文候选显示英文译词的流程完全一致** |
| `glossary-zh.qj` | 英 → 中 | 44,924 | 辅助。**通用英汉词典**（词频驱动），不是域表 | 用户已经输入**英文词** → 补中文释义 |

实测差别（同一批词）：

| 词 | `glossary-en` | `glossary-zh` |
| --- | --- | --- |
| 候选 | **n. candidate** | 候选人（通用词典义项，不是域义） |
| 输入法 | **n. input method** | **查不到**（多词技术术语缺失） |
| 学习 | v. study / v. learn | v. 学习 |
| 部署 / 翻译 / 天气 | v. deploy / v. translate / n. weather | v. 部署 / n. 翻译 / n. 天气 |

学英语的人学的就是自己领域里的词，**域表明显更贴**。因此手机建词流程要**接受中文输入**：中文查 `glossary-en` 得到英文词，英文词作为主键、用户输入的中文作为释义——与桌面流程一致。

两张表的**键空间不冲突**（`glossary-en` 键 ∩ `glossary-zh` 键 = 0，`glossary-zh` 无一个含汉字的键），所以自动判定方向是安全的。

本阶段**不做** ja/de/es/vi 的表：桌面遇到过的词仍走生词本同步，没遇到过的仍走 AI。

覆盖有限：中→英方向靠 `glossary-en`（23.2 万中文词，覆盖产品词库与短语层），只缺**产品词库之外**的中文词；英→中方向的 `glossary-zh` 只有 4.5 万英文词，生僻词查不到。查不到就记 `unknown`，仍走 AI，不拿近义词凑。

**`glossary-zh` 的缺口不能用「把 `glossary-en` 反转」补**，实测过：

| 指标 | 数字 |
| --- | --- |
| `glossary-en`（中→英）条数 | 232,213 |
| 反转后去重的英文键数 | 173,733 |
| `glossary-zh`（英→中）条数 | 44,924 |
| 两者交集 | 15,255（只占 `glossary-zh` 的 34%） |
| `glossary-zh` 有、反转查不到 | **29,669（66%）** |
| 反转有、`glossary-zh` 没有 | 158,478 |

反转的问题不是覆盖不够，是**反出来的不是释义**：

- **多对一严重**：14.2% 的英文译词对应多个中文词。`moth` → 124 个（全是什么蝙蛾、舟蛾、钩蛾的物种名）、`fish` → 100 个、`beautiful` → 70 个（丽、丽质、人美、优美）、`jade` → 65 个（玉、玉石、玒、玕）。
- **反转独有的 15.8 万词基本无用**：抽样是 `snow on pines`、`jade plate crab`、`lianyungang city`、`fangsong typeface`、`wumei pill` 这类从中文词库反推的生僻生物 / 地名 / 药品 / 字体专名。
- **交集里也没有可靠的挑选规则**：`glossary-en` 按码点排序（`㕮、㘎、㙘…` → `龟鹿二仙膏、龟龟…`），**没有词频**，挑不出「最常用」的那个。按码点序第一个取，交集 15,255 条里 **10,962 条（72%）取错**——`abandon` 取到「丢下」而不是「放弃」，`abalone` 取到「粗文九孔」而不是「鲍鱼」。
- `glossary-zh` 本来就**不是**反转产物，是独立生成的英汉词典：种子是 `english.tsv` 按 wordfreq 挑（≥2500）加技术词表全要，提示词要求「最贴切的中文对应词，**按常用度排**，多义词只取最常用的义项」。**「常用度」和「义项选择」这两个信号源表里没有，反转原理上得不到。**

**补法是扩大 `glossary-zh` 的词源**，不是反转：`tools/gloss-gen/src/args.rs:37-38` 的 `--min-frequency` 缺省 2500，降到 1000 可让入选词从 41,686 涨到 80,438（`english.tsv` 带词频的词共 94,568）。这是数据生成任务，不在本计划的代码改动里；静态表查不到时记 `unknown` 走 AI 的兜底照旧。

#### 静态表下发到手机，不查电脑

**表放在手机上，不放在电脑上。** 三个理由：

- **逐键搜索**：手机现有的词库搜索是子串匹配（`LearningStore.words` 是 `instr(lower(english), lower(?))>0 OR instr(meaning, ?)>0`，LIMIT 500）。每次打字发一次网络请求给电脑必然卡；远端的表也做不了子串 / 前缀搜索。
- **离线可用**：学习类 App 天天在手机上用，电脑不一定开着。
- **电脑端零改动**：表在手机，桌面端不需要加接口、不需要 Python 读器，中继工具这一块整条省掉。

**分发**：静态表随产品的 `data` Release 发布。`tools/release/data-bundle.sh:28` 已经把 `glossary-en.qj`、`glossary-zh.qj` 等放进 `qingjian-data.tar.gz` 并传到公开的 `data-vN` 预发布 Release（`tools/release/data-fetch.sh:34` 用免鉴权的 `curl` 下载，SHA-256 记在 `tools/release/data.lock`）。手机单独下这两个文件即可，不必下整个数据包（`lm.qj` 就有 42MB）。

#### 桌面与手机互相更新

随包表是**产品产物**，跟 `data-vN` Release 走就是最新的；桌面的表也是同一个 Release 装的，**随包表不走电脑同步**——通过电脑传 15MB 更慢更绕，还要求电脑在线。

**真正会落后的不是版本，是桌面攒下来的用户数据**：个人释义表 `user-glossary-<语言>.tsv`。桌面端上屏了随包表里没有的词，云端释义兜底生成一次就固化在这个文件里（`crates/qingjian-translate/src/personal_glossary.rs:11-12`，格式与随包表相同、用户可手改）。这些词手机没有，只能现问 AI。

所以「互相更新」拆成三路，各走各的通道：

| 数据 | 方向 | 通道 | 现状 |
| --- | --- | --- | --- |
| 生词本（译词 + 中文来源 + 计数） | 桌面 → 手机 | `GET /api/learning/context` | 本计划第一阶段 |
| **个人释义表**（桌面攒的 AI 释义） | 桌面 → 手机 | 随 context 一起下发 | **新增** |
| 手机学习档案（词卡 / 资料 / 测验 / 录音） | 手机 → 桌面 | `POST /api/learning/backup` | 已有（18 张表） |

**个人释义表由桌面端原样下发，差集在手机端做。** 桌面端只读 `user-glossary-<语言>.tsv`——它就在 `%APPDATA%\Qingjian\` 下，跟中继工具已经读着的 `user-vocab.tsv` 同一个目录，是**纯 TSV，零新依赖**。桌面端**不比对随包表**（那要它能读 `.qj`，得为此写一个 Python 读器，而随包表本来就该在手机上）。

手机端拿本地随包表做差集：只把「随包表里没有的」那些并入本地表，个人表优先。差集天然很小（用户实际遇到、且表里没有的词，通常几十到几百条），因此不需要截断策略，也不需要给个人释义表加时间戳（它现在只有 `HashMap<String, Translation>`，没有任何顺序信息）。

手机合并时**个人释义表优先于随包表**，与桌面端 `LayeredTranslator` 的「个人表优先、随包表兜底」一致。桌面端没给个人表的英→中方向（`glossary-zh` 只有随包表一个来源），那一路仍只有随包表。

**手机 → 桌面不需要新增通道**：现有备份已经把手机的学习档案传上去了；手机查静态表得到的释义是同一张随包表的产物，回传给桌面没有新信息。

#### 手机侧怎么读 `.qj`

格式很规整，一个 Kotlin 读器约 120 到 150 行：

```
Header 32 字节：magic "QINGJIAN" | version u16 | kind u16 | section_count u32 | reserved 16 字节
SectionEntry × N，每条 24 字节：tag[4] | reserved u32 | offset u64 | length u64
分节正文（8 字节对齐、小端）：
  TEXT  字符串 arena（UTF-8 字节）
  ENTR  EntryRecord 12 字节：word_start u32 | sense_start u32 | word_len u16 | sense_count u16
  SENS  SenseRecord 20 字节：text_start/reading_start/pos_start u32 | 三个 len u16 | reserved u16
  HASH  哈希索引（本端忽略）
```

依据 `crates/qingjian-format/src/layout/header.rs`、`layout/section_entry.rs` 与 `crates/qingjian-translate/src/glossary/{entry_record,sense_record}.rs`。

- **不复刻哈希函数**：线性扫 `ENTR` 建「词 → 条目」字典（23.2 万条，秒级），`HASH` 整节忽略。比复刻 FNV-1a + fmix64 简单，也没有两边哈希实现不一致的风险。
- 用 `FileChannel.map` 映射文件，按需切片，不整表读进内存。
- 查 `glossary-zh` 时键先做 ASCII 小写（它的键是小写，桌面端查找也是先原样再小写，见 `engine/commit/mod.rs:41-44`）。
- 查不到不报错、不猜、不返回近义词。

#### 手机侧的词汇查询

**词库页的搜索框扩成两个来源。** 现在它只搜本机 `words` 表（`LearningActivity.vocabulary()` → `store.words(query)`），搜不到新词。

| 搜到 | 显示 | 动作 |
| --- | --- | --- |
| 已添加的词 | 现在的词行 | 点开词卡（不变） |
| 静态表里的词（未添加） | 词行 + 词性 + 中文释义 | 「加入词库」→ 建卡：英文做主键、词性与释义已就位 → 例句 / 搭配 / 用法标「待补充」→ 「让 AI 补充」 |

**「让 AI 补充」走现有的流程**：`learning/notes/Job.kt` → `prepare_word_materials`。两处要改：

1. `notes/Job.kt:35` 现在只收英文（「此功能适用于 1～100 字的英文单词或短语」）。静态表已经把中文解析成英文做主键，这道校验**继续保留**即可——它验的是主键，不是输入。
2. `notes/Agent.kt` 的工具 schema 现在要求模型给**全部五个字段**（含 `meaning`）。静态表已经给了 meaning 与词性，**模型只补 example / translation / collocations / usage**，不重造 meaning。释义与词性以表为准。

#### 建词流程

- 词条加一个 `gloss_origin`：`desktop-vocab`（桌面生词本同步来的）/ `static-table`（查静态表补的）/ `ai`（手机自己生成的）/ `unknown`（两边都没有）。
- **建词接受中文输入**：用户在词条编辑里打中文 → 本地查 `glossary-en` → 英文词做主键、用户输入的中文做释义 → 英文成为不可改的主键。与桌面上屏中文候选显示 `glossary-en` 的英文译词是同一条路径。
- 用户直接打英文时：主键就是那个英文，本地查 `glossary-zh` 查到中文就填进释义，查不到就留空由 AI 补。
- **存储模型不变**：英文词仍是主键（`words.lookup`），中文仍是 `words.meaning`。「接受中文」只改输入侧，不改数据模型，也不改测验方向（`CHOICE` 仍是英文选中文）。
- **查不到的降级**：中文查不到 `glossary-en` 时不静默塞一个错的英文——提示「静态表里没有这个词」，让用户直接填英文，或走手机自己的 AI（`notes/Job.kt` 本来就有独立的 Koog 通道，不依赖电脑配对）。
- **没下载表时**：查表整体不可用，退回「用户手填英文 + AI 补全」。**表未下载**与**查不到这个词**是两回事，界面要分开说。
- 译词本身**不作为成绩**，也不进 `learner_model`，只是词条的内容。

#### 隐私

静态表是随包的公开数据，不含用户信息。查询在手机本地完成，**不新增任何网络请求**，也不新增输入原文、键串、候选列表或应用内上下文。

### 2.3 应用归因后置，必须有直接关联

现有 `CommitEntry.text` 是上屏内容，通常是中文；没有英文译词或相遇事件关联ID。`corrected` 是查询纠错，不是英文学习错误。禁止通过时间接近、中文来源匹配或同一分钟共现来冒充精确关联。

后续若需要应用分布，另加按 `language + word + local_date + app` 聚合的译词事件：

- Core 在实际记译词上屏/直接使用时关联已有应用标识；**挂点是 `VocabularyTracker::record_commit(language, word, used)`（`crates/qingjian-core/src/engine/vocabulary/tracker.rs`）与 `Engine::commit_translation(candidate, sense)`（`crates/qingjian-core/src/engine/commit/mod.rs`）**，不是 `Translator::learn`——后者是云端释义兜底回流写个人释义表的方向，不表示用户上屏。平台仍只提供应用信息，不在平台壳中实现学习逻辑。
- 应用标识在**事件发生的那一刻**取值落桶。`Engine::application` 是按会话存的（`crates/qingjian-core/src/engine/session.rs`），会话切换时随之 swap，组句中途也可能变，不能事后回查。
- 仅累计两个计数，命名避开与词汇本既有列混淆：
  `commit_with_gloss` = 带译词的中文候选被上屏的次数，等于词汇本的 `committed`；
  `gloss_typed` = 直接把译词打出去的次数，等于词汇本的 `used`。
  不新增输入原文、拼音或整句日志；不能将“带译词的中文上屏”称为“在该应用里打出英文”。
- 计数在内存更新，后台有界批量持久化；不让磁盘或网络等待阻塞候选生成。
- 按日分桶保留30天；缓存带schema、来源身份和覆盖日期。重启不重复累计，过期桶删除；历史没有关联的数据不回填应用名。
- 默认关闭，可在电脑设置启用。关闭后停止新增并移除对手机暴露的应用聚合；缺失数据表示未知，不以0集中度当作真实测量。
- 开启后只给前3个应用和 `other` 计数，名称最多64字符；通过已有配对接口传输。默认不向AI发送具体应用名。
- 不在阶段0加入未经证实的 `corrected` 词级计数。若今后回溯输入日志，须另行定义精确关联、撤销和去重契约及测试。

应用集中只表示使用集中，不能单凭浏览器或编辑器名称自动认定工作、职业或行业。第一版统一称“电脑常见词”；只有用户明确给定用途时才显示相应学习场景。

### 2.4 同步与目标回写

建立连接后沿用约30秒的检查节奏；来源拉取、上下文拉取和手机备份各自可失败、可重试。手动停止后不再启动新请求，迟到回调不能恢复连接或重建已清空资料。

手机成绩始终是手机侧事实；电脑来源只影响候选优先级。来源更新不覆盖非空手机笔记，中文原句不能当作已验证的英文练习材料。

可选的学习目标回写仅包含明确允许的偏好摘要，例如用途、新词数和分钟数。现有备份只导出学习表，没有 `StudyPreferences`；实施时需增加白名单字段及schema适配，不能假设已随备份传入。电脑仅只读展示，不回写手机偏好。
