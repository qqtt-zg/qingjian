## 一、现状与必须先修的前提

| 数据源 | 实际内容 | 当前限制 |
| --- | --- | --- |
| `user-vocab.tsv` | 语言、译词、三项计数、ISO首见/末见日期、认识标记、中文来源及原句 | 已有同步路由，但日期解析存在缺陷，不能当作已完成接入 |
| `vocab-log.tsv` | 相遇时间、语言、原文、译文、读音 | 没有稳定的应用关联键 |
| `input-log.jsonl` | 上屏内容、键串、查询纠错、应用、时间等 | 不包含对应英文译词，不能直接用于英文词级应用归因；`source=translation` 能识别“译词上屏”，但拿不到译词文本 |
| 手机学习数据库 | 词卡、答题、每日计划、录音评分、事件、记忆和用量 | 各来源字段及维度口径不同，尚无统一能力投影 |

### 1.1 先修复真实词库格式

现有 `tools/speech-relay/learning_sync.py` 将第3～7列一起转成整数，其中包含日期，导致合法的 `YYYY-MM-DD` 行被跳过。上游格式依据为 `crates/qingjian-learning/src/vocabulary_book/file.rs`，用合成但格式真实的fixture验证，不读取个人词库充当测试材料。

- 只将 `seen/committed/used` 三列解析为非负整数。
- `first/last` 按ISO日历日期解析。**日期缺失或非法时整行跳过并计入 `invalid_date_rows`，不做宽容处理。**
  理由：桌面端 `crates/qingjian-learning/src/vocabulary_book/file.rs:52-53` 对日期列用 `?` 短路，日期一坏整行丢弃，且下次保存时 `render` 重写文件把该词条**永久删掉**。
  中继端若改成保留，手机会看到一个桌面端认为不存在的词，两端判断相反，而且桌面端那一份还会被删词。
  `null` 只留给将来桌面端真的会写空日期的格式版本（目前 `render` 永远写满十列，不存在这种行）。
- 缺词、非法语言或负计数才跳过该行。协议明确日期单位，不继续使用未声明的Unix秒数假设。
- 同时修复手机 `Transfer` 对 `last` 的秒数解释。日期未知时不制造1970年或“今天接触”的记录。
- 合法的旧七列文件照读（“七列”指前七列含两个日期列都在，后三列走缺省：认识标记缺省为否、中文来源与例句缺省为空）；可选中文来源、例句和认识标记缺失时按“未知/空”处理；坏行不拖垮整份文件。
- **来源接口只有一个：`GET /api/learning/context`（见 2.1）。** 旧的 `/api/learning/words` 保持原样只作向后兼容，不再加 `schema` 参数——它没有 `language` 字段、没有窗口、没有截断，两个口径并排会出现“哪个是权威”的歧义。
- 新手机收到旧工具响应（新接口 404）时，只按已存在的数字 `last` 秒数契约兼容；旧工具此前丢掉的词不能由手机猜回，显示需要更新工具。发布前用构建30/31和新版交叉验证，旧版朗读和更新协议不变。

三项计数描述电脑接触，不是成绩。`committed` 是带此译词的候选上屏次数；`used` 才是直接打出译词的次数。`origin_text/example` 是中文来源及上屏原句，不保证是英文例句，也不直接证明发生了英文写作。

### 1.2 正确理解手机事件流

统一读取入口是 `archive.Store.events()`，它合并物理表 `learning_events`、`quiz_attempts`、每日题目和评测记录。只扫描 `learning_events` 会漏掉已有成绩。

`desktop_sources` 当前保存的是来源payload；实际字段是 `english/seen/committed/used/last/desktop_known/meaning/example` 八个（整行 JSON 原样存），其中**既没有 `source` 也没有 `known`**。不能把计划中的 `origin_text/known` 当作已经落库的字段。新旧payload经适配器读取。

待解决的断点是：来源没有用于排序、各项能力没有稳定投影、计划执行没有统一预算，以及模型请求成本没有覆盖整个执行链路。
